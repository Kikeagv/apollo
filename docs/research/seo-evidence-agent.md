# SEO de una landing page moderna en 2026 — matriz de evidencia

Investigación realizada el **2026-08-28**. Alcance: únicamente documentación
primaria/oficial de Google Search Central, web.dev/Chrome, schema.org y W3C.
“Confianza” expresa la solidez de la afirmación en la fuente; no implica una
garantía de ranking. Las recomendaciones son una traducción práctica de la
evidencia para una landing page.

| Afirmación | Evidencia visible | Fuente / título / editor / fecha / URL | Confianza | Límites o contradicciones | Recomendación práctica |
|---|---|---|---|---|---|
| Cumplir requisitos técnicos no garantiza rastreo, indexación ni publicación. | Search Essentials separa requisitos técnicos, políticas de spam y buenas prácticas; dice explícitamente que cumplirlos no significa que Google vaya a rastrear, indexar o servir la página. | [Google Search Essentials](https://developers.google.com/search/docs/essentials) — Google Search Central / Google — última actualización 2025-12-10. | Alta | La elegibilidad es condición necesaria, no promesa de inclusión o posición. | Definir SEO como embudo: accesibilidad técnica → indexación comprobada en Search Console → calidad/relevancia → conversión; no usar “pasa Lighthouse” como proxy de ranking. |
| `robots.txt` controla acceso de rastreo, no es un mecanismo fiable para ocultar una página del índice. | Google dice que `robots.txt` gestiona qué URLs puede solicitar el crawler y que para excluir una página hay que usar `noindex` o autenticación; bloquear el HTML puede impedir que Google vea el `noindex`. | [Introduction to robots.txt](https://developers.google.com/search/docs/crawling-indexing/robots/intro) — Google Search Central / Google — última actualización 2025-12-10. | Alta | Puede ser útil para tráfico de crawler o URLs irrelevantes, pero no para proteger información ni sustituir `noindex`. | Permitir HTML, CSS y JS necesarios para renderizar; usar `noindex` en páginas que no deben aparecer y reservar `robots.txt` para control de rastreo. |
| Un sitemap ayuda a descubrir URLs y expresa preferencia de URLs canónicas, pero no fuerza indexación. | La guía pide URLs absolutas y recomienda incluir solo las URLs que se quieren mostrar; también indica que `priority` y `changefreq` se ignoran y que `lastmod` debe ser verificable. | [Build and Submit a Sitemap](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap) — Google Search Central / Google — página oficial consultada 2026-08-28; fecha editorial no visible en el extracto. | Alta | Sitemap no sustituye enlaces rastreables ni garantiza indexación; es una señal, no una orden. | Publicar `/sitemap.xml` con HTTPS, solo URLs 200/canónicas/indexables, `lastmod` real y enviar/verificar en Search Console. |
| Consolidar duplicados mejora claridad y concentra señales, pero `canonical` es una sugerencia. | Google ordena las señales así: redirecciones (fuertes), `rel="canonical"` (fuerte) y sitemap (débil); puede elegir otra canónica. La documentación 2026 añade que canonicalización ocurre antes y después del renderizado. | [How to Specify a Canonical URL](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls) — Google Search Central / Google — última actualización 2026-07-10. | Alta | No hace falta declarar canonical en todos los sitios simples; señales contradictorias pueden hacer que Google elija otra. | Usar URL única HTTPS, canonical autorreferente en HTML, enlaces internos consistentes y redirecciones para variantes obsoletas; evitar que JS la cambie a otra URL. |
| URLs simples, descriptivas y estables ayudan a que usuarios y Google entiendan la página. | Google recomienda palabras legibles en vez de IDs largos, el idioma de la audiencia y guiones entre palabras; desaconseja fragmentos para cambiar contenido. | [URL Structure Best Practices](https://developers.google.com/search/docs/crawling-indexing/url-structure) — Google Search Central / Google — última actualización 2025-12-10 (documentación migrada/reorganizada en 2025). | Alta | Es una recomendación de comprensión y rastreo, no una fórmula de ranking aislada. | Para la landing, usar una ruta corta y estable (`/software-clinicas`), sin parámetros de campaña como URL canónica y sin `#/ruta` para contenido indexable. |
| Google procesa JavaScript en tres fases: rastreo, renderizado e indexación. | Googlebot renderiza con una versión evergreen de Chromium; no renderiza JS de archivos o páginas bloqueados. Las páginas 200 entran en cola de renderizado; las no-200 pueden saltarse. | [Understand the JavaScript SEO Basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics) — Google Search Central / Google — última actualización 2026-03-04. | Alta | JS no está prohibido y puede funcionar; SSR/prerender sigue siendo aconsejable por velocidad, bots que no ejecutan JS y fallos de renderizado. | Entregar en HTML inicial el título, H1, propuesta, prueba social principal y CTA; probar HTML renderizado, consola y recursos con URL Inspection/Rich Results Test; devolver 404/401 reales. |
| Los enlaces que Google rastrea deben ser anchors con `href`; el texto del enlace aporta contexto. | Google dice que no puede extraer fiablemente URLs de eventos de script, `span` o anchors sin `href`; acepta enlaces insertados por JS si terminan en markup HTML válido. Recomienda anchor text descriptivo y enlaces internos contextuales. | [SEO Link Best Practices for Google](https://developers.google.com/search/docs/crawling-indexing/links-crawlable) — Google Search Central / Google — última actualización 2025-12-10. | Alta | Google puede intentar interpretar formatos no recomendados, pero no es fiable; `nofollow` no debe aplicarse indiscriminadamente. | Convertir CTAs/navegación en `<a href="...">`; evitar `onClick` como único mecanismo, “click aquí” y menús que no exponen rutas; marcar enlaces pagados como `sponsored`. |
| Google genera automáticamente el title link usando varias fuentes, no solo `<title>`. | Puede usar `<title>`, título visual/H1, `og:title`, texto prominente, anchor text, enlaces entrantes y `WebSite`; puede reescribirlo si es vacío, inexacto, duplicado o inconsistente. | [Influencing your Title Links](https://developers.google.com/search/docs/appearance/title-link) — Google Search Central / Google — última actualización 2025-12-10. | Alta | No existe control manual del texto mostrado ni límite fijo de caracteres; cambios tardan en recrawlearse. | Hacer `<title>` único, conciso y descriptivo; alinear H1, copy visible, marca y `og:title`; no repetir keywords ni usar “Home” como único título. |
| La meta description puede mejorar el snippet, pero Google suele construirlo desde el contenido de la página. | Google dice que el snippet cambia según la consulta y usa `meta description` cuando describe mejor la página; no hay límite fijo, se trunca según el dispositivo y las descripciones repetidas no ayudan. | [Control your snippets in search results](https://developers.google.com/search/docs/appearance/snippet) — Google Search Central / Google — última actualización 2026-04-20. | Alta | No es garantía de texto mostrado ni una señal de ranking directa; una cadena de keywords es menos probable que se muestre. | Crear una descripción específica que resuma valor, audiencia y diferenciador; priorizar home y URLs críticas; mantener la promesa coherente con el copy visible. |
| Mobile-first significa que la versión móvil es la base de indexación y ranking. | Google recomienda responsive design; exige equivalencia de contenido, headings, metadata, `robots` y structured data; no cargar contenido principal solo tras interacción. | [Mobile-first Indexing Best Practices](https://developers.google.com/search/docs/crawling-indexing/mobile/mobile-sites-mobile-first-indexing) — Google Search Central / Google — última actualización 2025-12-10. | Alta | En responsive la misma URL/HTML simplifica el problema; un acordeón/tab puede ocultar visualmente contenido sin ser automáticamente spam si el contenido equivalente está disponible. | Auditar la landing con viewport móvil: mismo texto principal, enlaces, alt, canonical, structured data y CTA; no esconder el valor principal detrás de swipe/click o lazy load dependiente de interacción. |
| Structured data puede habilitar rich results y ayudar a desambiguar contenido, pero no garantiza apariencia ni ranking. | Google recomienda JSON-LD, exige que el marcado represente contenido visible y permite validar con Rich Results Test/URL Inspection; una acción manual de structured data elimina elegibilidad de rich result, no el ranking web ordinario. | [Introduction to Structured Data Markup](https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data) y [General Structured Data Guidelines](https://developers.google.com/search/docs/appearance/structured-data/sd-policies) — Google Search Central / Google — últimas actualizaciones 2025-12-10 y 2026-07-10. | Alta | Rich result depende de tipo, políticas, consulta, dispositivo y algoritmo; “válido” no equivale a “se mostrará”. | Marcar solo entidades y hechos visibles; usar JSON-LD mantenible, probarlo en staging y monitorizar errores; elegir el tipo que describa el foco real de la landing. |
| Schema.org aporta el vocabulario; para el comportamiento de Google manda la documentación de Google Search Central. | Google dice que la mayoría de sus formatos usa vocabulario schema.org y que existen propiedades schema.org no requeridas por Google; schema.org define `WebSite`, `Organization`, `LocalBusiness`, `Service` y propiedades como `name`, `description`, `url`, `image`, `sameAs`. | [Intro to Structured Data Markup](https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data) — Google Search Central / Google — 2025-12-10; [Getting Started](https://schema.org/docs/gs.html) y [Organization](https://schema.org/Organization) — Schema.org community / Schema.org — versión/uso visible 2026 (fecha editorial no uniforme). | Alta para la distinción; media-alta para elegir tipo | Schema.org no promete un rich result; no añadir tipos “por SEO” si no reflejan la página. `FAQPage` sigue siendo vocabulario, aunque Google retiró su apariencia. | Para una landing de empresa: considerar `Organization`/`WebSite`; `LocalBusiness` solo si hay negocio/local físico; `Service` si la página describe un servicio; enlazar identidad con URLs oficiales y `sameAs` reales. |
| En 2026 no conviene invertir en FAQ rich result de Google. | El changelog oficial indica que Google retiró la documentación de FAQ rich result y que la función dejó de aparecer en Search desde el 2026-05-07. | [Latest documentation updates](https://developers.google.com/search/updates) — Google Search Central / Google — actualización visible 2026-06-15; anuncio de deprecación 2026-05-08. | Alta | FAQ visible puede seguir ayudando a usuarios y schema.org sigue existiendo; la afirmación es específica del rich result de Google Search, no de otros consumidores. | Mantener preguntas/respuestas solo si resuelven objeciones reales; no crear FAQ artificial ni medir su éxito por una apariencia que Google ya no muestra. |
| El contenido generado o asistido por IA no está prohibido; producir muchas páginas sin valor sí puede ser abuso de contenido escalado. | Google pide contenido people-first, útil, fiable y original; menciona explícitamente páginas generadas con IA sin valor como ejemplo de scaled content abuse. | [Guidance on Generative AI Content](https://developers.google.com/search/docs/fundamentals/using-gen-ai-content) y [Spam Policies](https://developers.google.com/search/docs/essentials/spam-policies) — Google Search Central / Google — última actualización 2025-12-10 y 2026-08-28. | Alta | Google no exige revelar toda asistencia de IA; la evaluación depende del propósito, valor, originalidad y calidad, no solo de la herramienta usada. | Escribir claims verificables desde experiencia/producto real, editar por expertos, aportar datos propios y evitar páginas por ciudad/keyword o variaciones semánticas sin valor. |
| Para AI Overviews/AI Mode siguen aplicando SEO técnico y calidad; no hay “hack” especial de AEO/GEO. | La guía 2026 dice que las respuestas generativas se apoyan en páginas indexadas, crawlables y aptas para snippet; `llms.txt`, “chunking” obligatorio y schema especial para IA no son necesarios ni mejoran rankings. | [Optimizing your website for generative AI features](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide) — Google Search Central / Google — última actualización 2026-07-10. | Alta | Ser indexable y cumplir buenas prácticas tampoco garantiza aparecer en AI features; la guía no sustituye la documentación de cada formato. | Priorizar contenido no-commodity, estructura clara, imágenes/vídeos relevantes, rastreabilidad y Search Console; ignorar archivos o taxonomías creados solo para aparentar optimización de IA. |
| Cloaking, doorway pages, keyword stuffing, link spam y funcionalidades engañosas pueden causar democión o exclusión. | La política define estas prácticas y permite sistemas automáticos y acciones manuales; también aplica a manipular respuestas generativas. | [Spam Policies for Google Web Search](https://developers.google.com/search/docs/essentials/spam-policies) — Google Search Central / Google — última actualización 2026-08-28. | Alta | Una landing puede usar contenido dinámico, acordeones y tooltips legítimos; la diferencia es si se oculta/manipula para buscadores o si sirve a usuarios. | Revisar que bot y usuario reciban la misma propuesta; eliminar listas de ciudades/keywords, enlaces comprados, redirecciones engañosas, texto invisible y CTAs que prometen una función inexistente. |
| Los Core Web Vitals actuales son LCP, INP y CLS; “bueno” se evalúa en el percentil 75. | Chrome/web.dev publica umbrales: LCP ≤2.5 s, INP ≤200 ms y CLS ≤0.1; “pobre” es >4 s, >500 ms y >0.25 respectivamente, medido en el p75. | [How the Core Web Vitals metrics thresholds were defined](https://web.dev/articles/defining-core-web-vitals-thresholds) — Bryan McQuade y Barry Pollard / Chrome team — publicado 2020-05-21, actualizado 2025-05-07. | Alta | Son umbrales amplios y pueden cambiar con aviso; datos de laboratorio no sustituyen datos de campo. | Medir móvil y desktop con CrUX/PSI/Search Console; priorizar hero/LCP descubierto en HTML, no lazy-load del LCP, reducir JS de interacción y reservar dimensiones de imágenes/embeds para evitar CLS. |
| Core Web Vitals sí se usan en ranking, pero no existe una puntuación única de “page experience” ni un score perfecto que garantice posición. | Google dice que sus sistemas usan CWV, que no hay una señal única y que la relevancia puede prevalecer aunque la experiencia sea subóptima; otros aspectos mejoran usabilidad pero no ayudan directamente a rankear. | [Understanding Page Experience in Google Search](https://developers.google.com/search/docs/appearance/page-experience) — Google Search Central / Google — última actualización 2025-12-10. | Alta | Optimizar CWV solo por SEO puede no ser el mejor uso del tiempo; el impacto depende de consulta, competencia y calidad del contenido. | Establecer presupuesto de rendimiento y correlacionarlo con conversión; no sacrificar claridad, contenido o accesibilidad por perseguir 100/100. |
| WCAG 2.2 aporta criterios de accesibilidad que suelen mejorar comprensión y uso, pero no es una promesa de ranking. | W3C Recommendation 2024-12-12: alternativas para contenido no textual, estructura/relaciones programáticamente determinables, headings/labels, contraste, teclado y reflow; Google también recomienda semántica legible para usuarios y lectores de pantalla. | [WCAG 2.2](https://www.w3.org/TR/wcag/) — W3C Accessibility Guidelines Working Group; editores Alastair Campbell, Chuck Adams, Rachael Bradley Montgomery, Michael Cooper y Andrew Kirkpatrick — 2024-12-12; [AI optimization guide](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide) — Google — 2026-07-10. | Alta para accesibilidad; media para efecto SEO indirecto | WCAG es un estándar de accesibilidad, no una señal de ranking declarada; la accesibilidad no cubre todas las necesidades de usuarios. | Usar HTML semántico, H1/headings coherentes, alt útil, foco/teclado, contraste y reflow; comprobar que el CTA y la propuesta siguen siendo comprensibles sin depender de color, animación o imagen de texto. |

## Nota de método

- Se descartaron artículos de terceros, blogs no oficiales, agencias, estudios
  secundarios y consejos de “ranking hacks”.
- Cuando una página oficial no expone una fecha editorial uniforme, se marca
  como “fecha editorial no visible” en vez de inferirla del rastreo.
- Las recomendaciones que combinan dos fuentes (por ejemplo, Google + W3C o
  Google + Chrome) están señaladas por sus límites: la fuente puede probar una
  condición técnica sin probar causalidad de ranking.
